# Spare VRAM storage proposal (AI-assisted)

**Unverified design, not an implementation.** No capacity, speed, correctness or
hardware result is claimed. Existing port validation is Flycast-only; this pool
has not been validated even there. Flycast may not enforce the write-width rule,
so an emulator pass would not prove byte stores are safe.

## Allocation and address contract

Initialize the renderer with `pvr_init` first: KOS sets up graphics buffers and
initializes/resets its VRAM allocator during that call. Afterwards use
`pvr_mem_malloc`, check failure and retain the exact pointer for `pvr_mem_free`.
KOS documents 32-byte allocation alignment and `pvr_mem_available`; a proposed
storage budget must leave headroom for later textures and rendering allocations,
rather than taking all currently available space. See the primary
[KOS initialization source](https://github.com/KallistiOS/KallistiOS/blob/master/kernel/arch/dreamcast/hardware/pvr/pvr_init_shutdown.c)
and [allocator interface](https://github.com/KallistiOS/KallistiOS/blob/master/kernel/arch/dreamcast/include/dc/pvr/pvr_mem.h).

The uncached views at `0xA4000000` (64-bit/interleaved interface) and `0xA5000000`
(32-bit/sequential interface) map the **same 8 MiB**, with different bank ordering.
They do not supply two independent pools, and equal offsets do not always name
the same bytes. Keep the allocator's view throughout storage and retrieval;
changing just a base-address bit is not a valid general offset conversion.
Both views require **16-bit-or-wider writes**; reads can be byte-wide. Source:
[Marcus Comstedt's PowerVR memory description](https://mc.pp.se/dc/pvr.html).

The proposed transfer routine would issue explicitly aligned halfword/word writes,
including a padded final halfword for odd lengths, while preserving the true byte
length separately. Arbitrary `memcpy`, `memset`, packed-struct writes and compiler
generated byte tails are not acceptable without emitted-instruction review.
Start with a synchronous, CPU-controlled copy; DMA/store-queue paths would need
their own alignment, lifetime and completion design before adoption.

`pvr_mem_reset` invalidates all pool allocations, not just texture allocations.
The proposed owner must invalidate every storage handle before a reset,
shutdown or reinitialization. Never free or access an old pointer after reset:
it may now belong to a different allocation. The pool must not reset PVR itself.

## Proposed opaque handle API

These are contracts only; no API is installed:

| Operation | Proposed behavior |
| --- | --- |
| `store(source, length) -> handle/error` | Allocate rounded VRAM capacity, copy through bounded aligned main-RAM staging, and verify a round trip before publishing an immutable handle. Failure leaves ownership of the original source with its caller. |
| `fetch(handle, offset, length, destination) -> status` | Check generation and range, then copy to a caller-owned main-RAM buffer; never expose a VRAM pointer as an ordinary GOAL object or decoder input pointer. Bound each fetch so callers can stream a large item. |
| `release(handle) -> status` | Retire the handle and free its live allocator block once; reject double release and stale generations without touching memory. |

A small main-RAM table would track slot, generation, original allocator pointer,
logical length, rounded capacity and checksum. All operations would be serialized
with renderer allocation/reset ownership. A reset epoch prevents stale handles
from referring to reused slots; the staging buffer remains ordinary main RAM.

**It saves main RAM only if the original main-RAM copy is released.** Keeping both
copies merely consumes VRAM and adds staging/metadata overhead. Peak accounting
must include the source until transfer succeeds, staging, decoder history,
destination objects, allocator padding and graphics headroom. In particular,
copying today's ELF-embedded zstd romdisk into VRAM does not release that embedded
storage and therefore does not produce the desired saving.

## Candidate and exclusions

The best candidate in this port is **parking the next level's compressed DGO
during future level streaming**: prefetch compressed chunks, store them, release
their original heap buffers, then fetch chunks into main RAM as the loader needs
them. This is a proposal for the level-heap problem in
[MEMORY_BUDGET.md](MEMORY_BUDGET.md), not a change to current romdisk loading.
The decompressor's history and active linked objects stay in main RAM.

Display's DMA buffers are **not candidates**: they are active engine/transfer
resources with address, timing and producer/consumer contracts this storage API
does not satisfy. Engine code is **not a candidate** either: it must remain in
the executable native-code arena with its linker, cache and callable-address
contracts. No boot-arena increase or gameplay performance benefit follows from
this note.

Before any implementation claim, an asset-free experiment would need to check
odd tails, both-view alias awareness, checksums, exhaustion, stale handles,
reset/reinit invalidation and graphics coexistence, with disassembly proving
write widths. Flycast results would remain emulator evidence only; hardware
behavior, available headroom and any worthwhile speed/RAM tradeoff remain open.
