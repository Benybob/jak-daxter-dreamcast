# Original retail data-object format

2026-10-21. AI-assisted work. The full native game remains unfinished.

`goal_object.c` is a shared Windows/SH-4 read-only validator for the original
single-segment V2/V4 data-object format. This is separate from the trusted
in-memory native function module format. Retail V3 code objects are rejected;
their MIPS instructions cannot execute as SH-4 instructions. The original
decompiler also distinguishes these retail formats from desktop object headers.

V4 has a sixteen-byte outer header, data, then a V2 header and relocation table.
V2 stores its header/table first and data afterward. The parser checks both
headers and their lengths, four-byte data alignment, pointer seek/fix runs,
255-byte continuation/mode changes, variable-width import deltas, bounded names,
symbol/type/empty imports, exact placeholders, duplicate patches and zero link
padding to a 64-byte boundary. Pointer targets must lie inside the data segment
or exactly one past its end. Such an address does not authorize a dereference.
It leaves source bytes unchanged and never executes relocation methods or code.

Inputs are bounded to 8 MiB. A temporary bitmap uses approximately one byte per
32 data bytes to reject duplicate patch locations. Names borrow the input
buffer. Visitors can observe a valid prefix before a later error; a mutating
loader must fully validate before applying updates or must roll back changes.
The scanner itself does not allocate native game objects or resolve imports;
the separate transactional loader below performs those operations.

The host audit of this user's validated ntsc_v2 data found 668 V4 objects across
36 DGO/CGO archives. **All 668 pass**. An initial stricter rule rejected 27
texture pages; inspection found all 52 targets exactly at the data end, in
zero-length texture-page segments. The pinned decompiler permits this boundary.
The native profile now preserves exact one-past addresses and continues to
reject targets beyond the end. All 52 cases were checked against zero segment
sizes in the original bytes and the texture-page-segment layout in texture-h.gc.
The other 1,116 objects have non-V4 headers and are outside this data-only audit.
Large valid segments also need bounded streaming before broad stock-RAM loading.

The stock-16-MiB Flycast target passes **182/182 checks**, including the unmodified
224-byte `game-cnt` object from GAME.CGO: a 144-byte data segment with one import
of `game-count-info`. It validates real original bytes without repacking the
object format and now links that data with a native type reference. The broader
host suite passes **85 tests**, including 64 shared C loader assertions. The separate native
GOAL/runtime suite passes 775 checks; these results must not be conflated
with original kernel boot or whole-game execution.

The audit exits nonzero if any V4 object fails and saves all object names,
hashes, sizes and individual results. A build without `--retail-archive` needs
no game data and runs 98 synthetic native format/load checks. Supplying the local
archive adds seventeen format/load checks using the actual object; no ISO or asset download is
performed. Generated bytes and SHA-256 provenance are in `build/object_fixture.*`.
The optional art archive adds 67 checks of the original 1,344-byte warpgate
asset, including all 48 native pointer/import fixups and all 236 untouched words.
Its native root, nested name string, element count, false symbol and geometry
pointer are checked against the original layout. The canonical fixed art-group
slot is bound before loading. This is asset linking, not animation or drawing.

## Native V4 data relocation

`dc_goal_load_data_object` accepts V4 data segments up to 2 MiB. It performs a
complete read-only validation before allocating the destination or interning
imports, then snapshots the 262,144-byte symbol table and saves arena state.
The second scan rebases internal pointers and resolves symbol/type/empty-list
references into the native runtime. A late error restores symbol names, values,
counts and arena usage; the result stays empty. Existing type metadata is not
changed by import resolution. Source bytes remain immutable. No original
relocation method, MIPS instructions or startup are executed.

Original type interning rules are retained: method hint 0 selects 12 slots;
hint 1 selects 44, and an existing type ignores those default-count hints.
V4's unknown-count type marker uses hint 1. A new forward type has no invented
parent or object size. Later native deftype startup refines its metadata while
preserving identity and capacity. Explicit capacity growth or non-type bindings
are rejected. Required fixed kernel bindings must be installed before loading
assets that reference them; the complete kernel namespace remains unfinished.
The diagnostic now calls `dc_goal_install_kernel_types` before loading data;
see `KERNEL_TYPES.md` for its 35 original type definitions and asset placeholders.

The result reports the raw data-segment base/size, consumed arena bytes, import
and patch counts and transient snapshot-plus-bitmap bytes. The object's root
tag and fields retain their original offsets; the loader does not assume every
segment has the same root structure. These resource counts exclude source
buffers, executable, KOS, ordinary stacks and allocator overhead. The 8 MiB
scanner limit does not imply every valid object can be loaded on stock hardware;
larger objects and full levels need streaming and a complete residency budget.

Shared host/SH-4 tests cover internal/native pointers, canonical fixed imports,
forward declarations and later definition, source immutability, duplicate loads,
late type failure, OOM after a new symbol allocation, exact table/arena rollback,
V2/V3 exclusion, invalid arguments and an over-budget but structurally valid
data segment. The retail case preserves all 140 non-tag payload bytes of
game-cnt while replacing its type word with a native game-count-info reference.
